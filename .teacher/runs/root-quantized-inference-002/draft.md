## Problem

EXL3 inference must turn packed trellis states into linear-layer products while preserving channel scales, Hadamard transforms and the quantizer’s tensor-core ordering. This implementation provides both direct quantized multiplication and reconstruction followed by dense multiplication. [source; call_1e16a410475a42dead5424a8d77841a1, call_ffb15fe60cf441e19e9c2ecbba79a9f4, call_57a5c46a53b249c38bd373e2b9bc1821]

## Reasoning

The two execution paths expose a memory-versus-computation tradeoff: direct GEMM decodes compressed tiles into registers, whereas reconstruction allocates a full FP16 inner-weight matrix for cuBLAS. The default crossover at 32 flattened input rows is an implementation heuristic, not a demonstrated performance boundary. [inference; call_1e16a410475a42dead5424a8d77841a1, call_fb6ec8eba7ff48bdb332a4e05a6df917, call_da2c89e6fad24f08bbbaa5f04ec4f478]

## Impact

Linear layers can load EXL3 tensors preferentially, retain an FP16 alternative, and override reconstruction through the forward parameters. Both EXL3 paths share the packed-state decoder, but their accumulation and intermediate rounding differ. [source; call_d1ce61dc203e499d9692ad5c7e9414e6, call_1e16a410475a42dead5424a8d77841a1, call_4946713eee294bd7974f23d5c5a4c9fa, call_2fd635db46594ee192abc9f3fc5294d8]

## EXL3 loading, reconstruction and direct quantized GEMM

Loading establishes the representation contract. Linear.load tries EXL3 under the primary and alternate keys before trying dense weights. load_exl3 requires trellis plus an input-side su/suh alternative and an output-side sv/svh alternative, loads them onto the selected device, and includes optional bias. LinearEXL3 requires an int16, three-dimensional trellis; packed signs are int16, while unpacked scales and bias are FP16. It derives the bitrate b from trellis.shape[-1] // 16. Although loading still requests an optional .scale tensor, the constructor rejects a non-None scale. The current quantizer instead emits suh, svh and trellis, with scaling incorporated into the channel vectors. [source; call_d1ce61dc203e499d9692ad5c7e9414e6, call_1e16a410475a42dead5424a8d77841a1, call_df8fb28b8d134d7bb21de020c91c2ed0]

The transform order explains how compressed inner weights become a normal linear layer. For inner matrix Q of shape (k,n), the unpacked-scale path implements the algebraic weight D(suh) Hk Q Hn D(svh), where Hk and Hn are blockwise normalized 128-point Hadamards. forward flattens the leading input dimensions, computes xh = (x multiplied by suh) Hk, multiplies xh by Q, applies the output Hadamard and then svh, restores the output shape and adds bias. A packed sv selects sign flips instead of general output scaling. This is an algebraic description; the implementation introduces FP16 rounding between stages. [inference; call_1e16a410475a42dead5424a8d77841a1, call_2612d7d72682438db41c567bd6f65485, call_ffb15fe60cf441e19e9c2ecbba79a9f4]

LinearEXL3.forward defaults to reconstruction when the flattened row count m is at least 32; params['reconstruct'] overrides that choice. Despite the variable name torch_mode, this branch calls get_inner_weight_tensor, ext.reconstruct and ext.hgemm—not torch.matmul. It allocates a fresh zero-filled FP16 (k,n) matrix on each call, then applies the output Hadamard separately. The direct branch calls exl3_gemm on the packed trellis. With packed sv, that kernel also performs the output Hadamard and signs; with the currently emitted svh, Python invokes a separate Hadamard and multiplies by svh afterward. [source; call_1e16a410475a42dead5424a8d77841a1, call_df8fb28b8d134d7bb21de020c91c2ed0, call_2fd635db46594ee192abc9f3fc5294d8]

Packing stores transitions rather than independent 16-bit indices. Each 16×16 tile contains 256 positions and occupies 16b int16 words, giving trellis shape (k/16,n/16,16b) for b=1…8. pack_trellis_kernel keeps each state's low b bits, writes them in stream order and swaps the 16-bit halves of each 32-bit storage word. Dequantization recovers a 16-bit trailing window ending at position (t+1)b; adjacent windows overlap by 16−b bits, and modulo addressing wraps within the tile. The +256b offset keeps the beginning-of-tile window arithmetic nonnegative while implementing that wrap. [source; call_166d63c7be614d809427ceb0c5fedebb, call_0c07ccdb4dde4b589c0a3e291cbeaac6, call_ffb15fe60cf441e19e9c2ecbba79a9f4]

dq_dispatch converts eight consecutive states into two FragB register fragments. Bitrates 1 and 2 use dq8 with four-state shift reuse, bitrate 3 uses two-state reuse, and bitrate 4 has a dedicated aligned extractor. Bitrates 5, 6 and 8 use two dq4 calls; bitrate 7 uses paired dq2x2 calls. These specializations exploit the lane-aligned windows rather than repeatedly extracting every state independently. decode_3inst_2 then performs unsigned 32-bit affine mixing, mask/XOR construction of half values, and a half2 addition. This is procedural decoding, not a table lookup or ordinary integer-times-scale dequantization. The alternative 2MAD decoder exists but is not selected by this inference path. [source; call_0c07ccdb4dde4b589c0a3e291cbeaac6, call_45b4ff4daf3541c2a90c7fe83cd7df78, call_6bbe069e223b44bbb29c1c3372856a40]

Tensor-core order is retained to make those eight decoded values immediately usable. tensor_core_perm assigns lane t the rows 2(t mod 4), that row plus 1, plus 8 and plus 9, at columns floor(t/4) and floor(t/4)+8. ldlq applies this permutation before quantization, undoes it only for reconstructed values, and leaves encoded states permuted. In GEMM, load_frags requests offset floor(t/2)×16+(t mod 2)×8 = 8t and decodes directly into the two B fragments consumed by m16n8k16 MMA instructions. Thus the direct path avoids a decoded-weight rearrangement through shared memory. The quantizer chapter covers how these encoded states are produced. [source; call_ffb15fe60cf441e19e9c2ecbba79a9f4, call_fb6ec8eba7ff48bdb332a4e05a6df917, call_6bbe069e223b44bbb29c1c3372856a40]

Reconstruction pays the layout-conversion cost explicitly. reconstruct_kernel processes a 16×128 region using 256 threads: eight warps decode eight packed 16×16 tiles with the same dq_dispatch used by GEMM. Each warp shuffles values from the lane four positions ahead, interleaves half values into a shared row-major tile, and writes contiguous output vectors. get_inner_weight_tensor returns only this decoded Q. get_weight_tensor additionally applies the left/right Hadamards and channel factors, making full weight reconstruction a distinct operation from the reconstruction used during forward. [source; call_4946713eee294bd7974f23d5c5a4c9fa, call_1e16a410475a42dead5424a8d77841a1, call_2cac34182a2e48348b4877ec99b08221]

A bounded CPU check verified all 256 permutation positions form a bijection, the argsort inverse restores row-major order, and the reconstruction shuffle/store mapping restores all 256 labeled positions. It also compared scalar emulations of packing and the selected dq_dispatch extraction paths against circular bit-string windows: 32,768 windows matched across 16 deterministic random tiles at each bitrate 1…8. The emulation explicitly masked 32-bit packing arithmetic and modeled the swapped half-word storage. These results validate the checked indexing identities, not CUDA execution or the floating-point decoder. [execution; call_4cebfc52595947b8b6b29939b74b4476]

Direct GEMM pipelines compressed data rather than materializing Q. exl3_gemm_kernel asynchronously copies row-major A and packed B tiles into shared-memory stages, loads A with ldmatrix, decodes B into register fragments, and invokes FP16-input/FP32-accumulator m16n8k16 instructions. All but variant 1 use two fragment stages; the source explains that alternating explicit iterations helps interleave dequantization without spilling fragment arrays to local memory. Work is sliced across the k×n tile space. Partial k sums are reduced within a block, then ordered across blocks by per-output-tile locks. Cross-block intermediate sums are stored in FP16 C, so FP32 MMA accumulation does not imply an entirely FP32 reduction. [source; call_fb6ec8eba7ff48bdb332a4e05a6df917, call_2fd635db46594ee192abc9f3fc5294d8, call_6bbe069e223b44bbb29c1c3372856a40]

The optional fused output transform runs only after the final reduction. It reloads FP16 C, combines a four-element transform with 32-lane XOR-shuffle stages, normalizes, applies packed signs and writes FP16 output. The separate had_r_128 uses the same 128-point structure, with FP16 input prescaling and floating-point transform arithmetic. Its 0.088388347648 normalization represents 1/√128; the scalar calculation returned 0.08838834764831843. Fusion here removes a separate transform launch, but does not eliminate the intermediate global-memory C write/read. [source; call_2fd635db46594ee192abc9f3fc5294d8, call_2612d7d72682438db41c567bd6f65485, call_4cebfc52595947b8b6b29939b74b4476]

Six native variants are available, expressed as (tile m,k,n; shared stages; fragment stages): 1=(16,16,128;3;1), 2=(16,32,256;4;2), 3=(16,32,128;4;2), 4=(32,32,128;4;2), 5=(64,16,128;4;2), and 6=(16,16,512;4;2). launch rejects k or n not divisible by the selected tile dimensions; partial m tiles are supported. The public EXL3 forward also requires FP16 input and k divisible by 128 through had_r_128, while output transform/reconstruction paths require n in complete 128-channel groups. The native comments are not a complete validation contract: actual launch checks and transform indexing determine these constraints. [source; call_57a5c46a53b249c38bd373e2b9bc1821, call_a664fafe103341b685b362989843904a, call_fb6ec8eba7ff48bdb332a4e05a6df917, call_2612d7d72682438db41c567bd6f65485, call_4946713eee294bd7974f23d5c5a4c9fa]

select_kernel is a fixed shape/device heuristic. OLD and Ampere categories use variant 4 above 16 rows, otherwise variant 3 for n<2048 or variant 2 when n is divisible by 256. Ada uses a 50-million-weight threshold for small-m selection and an 8-million-weight threshold for larger m. Hopper/Blackwell additionally select variant 6 for m≤16 when n≥65536 or k×n≥200 million, provided n is divisible by 512; above 32 rows they choose variant 5 for matrices of at least 8 million weights. These numbers classify matrix size, not quantization accuracy. A positive force_kernel_idx bypasses selection; otherwise the Python caller passes −1. An incompatible selected variant returns zero, which LinearEXL3.forward does not inspect or replace with reconstruction. [source; call_57a5c46a53b249c38bd373e2b9bc1821, call_1e16a410475a42dead5424a8d77841a1]

Launch sizing contains additional resource assumptions. Every variant requests 90 KiB dynamic shared memory, identified in the source as the compute-capability-8.6 maximum. The slice count is min(SM count, floor(number of k×n tiles/12)); the source labels 12 experimental. Scalar arithmetic confirmed that the declared shared arrays fit the budget for all six variants at the maximum bitrate, requiring 11,776 to 40,960 bytes. It also showed that k=n=128 with a 32×128 k×n tile yields zero slices. Thus valid transform dimensions alone do not guarantee a nonzero launch grid. [execution; call_4cebfc52595947b8b6b29939b74b4476, call_57a5c46a53b249c38bd373e2b9bc1821, call_fb6ec8eba7ff48bdb332a4e05a6df917]

The dense alternative shares the same linear-layer interface without the EXL3 transforms. LinearFP16 transposes loaded (out,in) weights into contiguous (in,out) storage, converts float32 weights to FP16, and invokes hgemm before bias and output reshaping. hgemm implements row-major multiplication through cublasHgemm by reversing operand order and m/n arguments, with alpha=1 and beta=0. LinearFP16_torch is also exported and wraps nn.Linear, but the inspected loader chooses LinearFP16, not that torch alternative. Reconstruction therefore reuses the dense cuBLAS backend while retaining quantized storage between calls. [source; call_1932d59907964723b84ed037dfe3f6c7, call_da2c89e6fad24f08bbbaa5f04ec4f478, call_41c2e2a053604343b62e97916e7992d6, call_d1ce61dc203e499d9692ad5c7e9414e6, call_1e16a410475a42dead5424a8d77841a1]

## Uncertainty and limits

No CUDA kernel, cuBLAS comparison, model inference or performance benchmark was executed. The successful run was a standard-library CPU check of integer packing, indexing and resource arithmetic; it did not test decoder floating-point values, GPU synchronization or numerical agreement between execution paths.

Packed-input-sign support is incomplete in the inspected Python path: LinearEXL3 accepts su, but forward passes only suh to had_r_128. get_weight_tensor also uses tensor truth tests for su and sv rather than explicit None checks. These paths were not exercised.

The wrappers do not fully validate their storage contracts. In particular, reconstruct uses cols // 8 without checking the output-width remainder; direct GEMM does not provide an automatic fallback after an incompatible launch selection; and its slice-count heuristic can produce a zero-sized launch grid for small matrices.

Kernel thresholds and architecture categories are inspected dispatch policy, not evidence of optimality or validated hardware support. FP16 intermediate storage also prevents assuming bitwise equivalence between direct GEMM, reconstructed GEMM and full-weight reconstruction.
