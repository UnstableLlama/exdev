## Installation, examples, and evaluation boundaries

Installation offers two paths: install requirements.txt followed by pip install ., or set EXLLAMA_NOCOMPILE for a JIT-mode installation. setup.py uses the presence of that environment variable—not its value—to disable precompilation. Otherwise, when Torch is already available, it gathers C/C++/CUDA sources into a CUDAExtension built through PyTorch. The README also permits running scripts directly from the checkout. It requires FlashAttention-2, reports no release builds or ROCm support, and identifies cache quantization and tensor parallelism as missing; a HIP compiler flag in setup.py does not establish working ROCm support. [source; call_5ba43b65301a41e3b392317aa6259629, call_eab125d8f4e6444f961f305b67a1a3bf]

Dependency installation is not interchangeable across the two lists: requirements.txt specifies Torch >=2.6.0, flash_attn >=2.7.4.post1, tokenizers >=0.21.1, and NumPy >=2.1.0, while setup.py permits Torch >=2.2.0 and omits flash_attn and tokenizers from install_requires. Evaluation dependencies are separated into requirements_eval.txt, including HumanEval 1.0.3 and several comparison backends; requirements_examples.txt adds blessed for the terminal display. MANIFEST.in explicitly includes Hadamard data files. [source; call_29178b6ca290458d8a8f78edc16b2604, call_eab125d8f4e6444f961f305b67a1a3bf, call_a7ba86a0a81d4f8283f00898026f4564, call_257188d350ae46ab8c823584dac0347f, call_bbda9840f39443a696c08ad4f99e191a]

The documented conversion interface is python convert.py -i <input_dir> -o <output_dir> -w <working_dir> -b <bitrate>. The working directory holds checkpoints and quantized tensors pending compilation and should fit an output-model copy. Resumption requires an explicit -r/--resume, unlike the documented EXL2 default. These instructions connect users to conversion; they do not demonstrate conversion speed or successful recovery. [source; call_5ba43b65301a41e3b392317aa6259629]

examples/generation_loop.py exposes the low-level inference contract: construct Config, Model, and Cache before model.load(); tokenize the prompt; prefill all but its final token; then forward that final token with past_len equal to context length minus one. Each sampled token is appended and becomes the next input. The example supplies flash_attn, cache, and a rectangular batch_shape of (1, 2048), checks token stop conditions, and streams vocabulary pieces. examples/generator.py offers the higher-level alternative: generate() for complete single/batched outputs, or enqueue Job objects and route iterate() result chunks by identifier. Its temperature sweep demonstrates a sampler option, not a quality evaluation. [source; call_c3116b3fe85645bdb4972833dec8beee, call_286847ff6d4843ee92854aadfd7f95ac]

The interactive entrypoint is python examples/chat.py -m <model_dir> -mode <mode>. It formats and retokenizes conversation history, reserves room for the response, removes oldest turns when necessary, and streams a Job's text updates. chat_templates.py supplies raw, llama3, chatml, phi, mistral, and gemma formats with explicit BOS and stop-token policies; these are application-side templates, not architecture validation. The separate common.py helper labels its templates approximate, contains an extra literal 'n' in the Mistral prompt, and has no Mistral branch in get_stop_conditions. [source; call_5ba43b65301a41e3b392317aa6259629, call_6e4782a2547d422a9ed04355d8e03698, call_c3954153f80047d0a343ef129e4c1cec, call_c72d5456515447baace33fcf5addea2a]

dynamic_gen.py demonstrates queueing many prompts against a shared 32768-token cache, a batch limit of 16, and 2048-token prefill chunks. Its comment states the tradeoff: smaller chunks reduce pauses when jobs start but sacrifice prompt-ingestion throughput. async_generator.py instead wraps jobs as async iterators gathered concurrently, explicitly cancels one early-exited job, and closes the generator. banned_strings.py contrasts jobs with and without phrase suppression and displays suppressed_text separately; it also changes min_new_tokens between those conditions, so it is a feature demonstration rather than a controlled comparison. [source; call_b26d0c0066c545de9a3937345fcc8a8b, call_a17f1195bae7453d93d26775c14a1880, call_dd22cd22e9fd4d388f594dc1a262ea84]

eval/ppl.py measures next-token likelihood on Wikitext-2 raw test text joined with double newlines. It tokenizes with the loaded model's tokenizer, makes 2048-token windows at stride 512, defaults to 100 rows, and forwards each window without a KV cache using flash_attn_nc. It slices logits to the actual vocabulary, applies float32 log_softmax, gathers the following token's log probability, and reports exp(-sum(log probability)/target count). Every window contributes all 2047 next-token targets; overlapping targets are not masked away. [source; call_18a766598ce94204a10329e055e71cb6]

eval/compare_q.py separates dataset preparation from backend loading and forwarding through named function tables. Dataset and perplexity functions use disk-cache decorators; --clear_cache invalidates selected test_ppl entries. Model specifications are JSON arrays, despite the CLI help saying JSONL, and wildcard filenames can combine them. The runner emits JSON results and optionally plots perplexity against decoder bits per weight or decoder-plus-head storage. Unlike ppl.py, it does not slice the logits vocabulary before softmax. The supplied Wikitext specifications use length 2048 and stride 512, capped at 20 or 100 windows. [source; call_2daf930a08484ddd86794564f60f9d70, call_3d36342c31f649b6bd61a360d92a9fe4, call_618c2d9afbf840db981f5b9c4fbe8431, call_bb74ed980c314a41ac907b2269ae4d6a]

A bounded Python check reproduced the window-target indexing. Assuming enough source tokens, 20 windows score 40,940 target occurrences but only 11,775 distinct target positions; 100 windows score 204,700 occurrences over 52,735 distinct positions. Maximum multiplicity is four. Thus the configured statistic weights overlapping predictions, including predictions with different available context, rather than scoring each corpus position once. This checks indexing only, not tokenization or perplexity values. [execution; call_6993685a93164d89bf14c7050229fd61]

Backend adapters normalize their outputs to logits but retain different execution paths. ExLlamaV2 uses autosplit with a cache required for loading but not used by its evaluation forward. ExLlamaV3 loads for 2048-token output and forwards in flash_attn_nc mode; it can also overlay tensor files supplied alongside a model directory. llama.cpp resets state for each sequence, requests all logits with a 2048 context, and transfers scores to CUDA. Transformers loads in half precision on cuda:0 or device_map='auto' and receives the common token IDs. Sharing IDs controls one input variable but does not itself establish vocabulary compatibility across artifacts. [source; call_2a11de57e9d7487f88ca83a38aaa3389, call_3da8b9e429ec4bf6bc0367db53118a02, call_5c3cf9f4c40e455e94a35b68c8771d57, call_322572cabc7f499da0eb4ea38eee3fa7]

The comparison plot's 'VRAM' is calculated tensor storage, not measured peak GPU allocation. Adapters count decoder linear weights/quantization tensors and the output head, then convert bits to bytes and divide by 1024^3. This excludes runtime caches and workspaces. Accounting is backend-specific: GGUF recognizes projection names and falls back to token embeddings for a tied head; Transformers recognizes several quantized module classes and uses out_features >= 0.9*vocab_size as a head-identification heuristic. That 90% cutoff is an implementation heuristic, not a verified architecture invariant. [source; call_2daf930a08484ddd86794564f60f9d70, call_2a11de57e9d7487f88ca83a38aaa3389, call_3da8b9e429ec4bf6bc0367db53118a02, call_5c3cf9f4c40e455e94a35b68c8771d57, call_322572cabc7f499da0eb4ea38eee3fa7]

The model specifications configure comparisons for Llama-3.1 70B/8B Instruct, Llama-3.2 1B Instruct, and Mistral-7B-Instruct-v0.3. They include EXL2/EXL3 bitrate sweeps and alternatives such as GGUF, AQLM, AWQ, VPTQ, BNB, and an HF FP16 baseline. These files contain local paths, dispatch names, and labels—not scores. Even labels need care: the 70B EXL3 specification assigns the same 'EXL3 1.6bpw H3' label to two different paths. [source; call_061ab7db673c47b88599a3920f90a44c, call_ced792c6e0b6411382ad1f1e74553538, call_f7a0d5772c1242a38500fefd099fd517, call_f62eaa3ce53440aeb28af1dd87f9e249, call_17573d466fde476eb9705f757618c598, call_0e984eaddae548b2968dfa6ddb4696cf, call_4cbeb21284504b02bdf66aee33e764c9, call_6b2586982ee241a49b64a705af7c0524, call_916436e158a7423fb3d046fbc7898df9, call_59194335c63a49708737968a58d32890, call_1da4c7b906244756876109d6d4e03c06]

eval/model_diff.py is a layerwise divergence diagnostic, not a language-quality score. It tokenizes Wikitext with model A's tokenizer, advances independent hidden states through zipped top-level module lists, and loads/unloads one module at a time to limit residency. It prints mean per-row Frobenius-relative error and maximum absolute difference divided by model B's row norm. Differences therefore accumulate through earlier modules; the script does not isolate each layer using identical incoming activations or assert that the two module lists match. [source; call_bc183882bd294050b710f3773cb3e4d6]

eval/humaneval.py generates code-completion samples and optionally delegates functional checking to evaluate_functional_correctness. Defaults are 200 samples per task, top_p=0.6, temperature=0.6, and a 768-token cap; jobs use token healing, a six-token minimum, EOS stopping, and a generator batch limit of 256. The collector additionally ends a sample at a non-indented final line, cancels unfinished jobs, and writes task_id/completion records to JSONL. Prompt formatting and this extraction heuristic are part of the evaluation protocol. Merely generating the file does not establish functional correctness or a pass rate. [source; call_6d844bdcbb4445019d0e34c5689a03a2]

The science scripts probe narrower mechanisms. codebook_eval.py decodes all 65,536 16-bit states, prints RMS, plots a 256-bin histogram, and draws 20,000 transition pairs for each K=1..8 using ((state<<K)|new_bits)&0xFFFF. gumbel_eval.py compares GumbelSampler with softmax-plus-multinomial on one synthetic 128,256-logit distribution, using 250,000 samples and diagnostics every 10,000. Its 1e-5 floor clamps both empirical and reference probabilities; despite comments about ignoring small probabilities, those entries are not removed. [source; call_bb6c5266aa4e40fa94e40eaadb5dfce4, call_e118ac7813bd4326a5d1089682613765]

science/qgemm_benchmark.py times kernel variants rather than checking correctness. It sets K=8, tries several matrix and batch shapes on three hardcoded devices, queries the preferred kernel, skips incompatible variants, performs ten warmups, and averages 200 calls. It cycles cloned buffers whose nominal combined size exceeds an assumed 512 MiB cache budget to reduce L2-residency bias; that number is an assumption, not detected hardware capacity. Scalar .item() reads bracket timing to wait for GPU results. The table marks the preferred kernel 'OK' when its relative latency gap from the fastest tested variant is at most 1%; no resulting timings are supplied here. [source; call_bff2d2ca24ad41f7b7c5eb406d361bb9]

The numerical tests compare specific paths rather than proving end-to-end correctness. test_ext_norm.py checks RMS normalization against float32 reference arithmetic across input/output dtypes and shapes, including in-place operation, with rtol=atol=1e-3; it separately exposes synchronized benchmark cases. test_rope.py compares native and Torch application for scalar offsets, batched offsets, and explicit position IDs at 1e-6 tolerance, but enables only NEOX style with theta=1, full rotation, and no scaling. test_qgemm.py compares direct quantized forwarding with reconstructed forwarding for eight selected projections/head and ten batch sizes, accepting rtol=atol=0.05. Both GEMM paths use the same quantized model, so this is not a comparison to original unquantized weights. [source; call_5d03729f7e7b42d5829a2702b8d5e715, call_35a486c39bf44f24b002f98fec246302, call_57d8965abcfb44639e0b6594116633fb]

test_quant_fn.py checks three distinct properties: tail-biting and normalized MSE for random tiles (currently parametrized only at K=1), near-lossless re-encoding of synthetically valid decoded sequences for K=1..8, and layer conversion/reconstruction using Hessians captured from random activations. Conversion checks use explicit K-dependent proxy-error and weight-tolerance tables. assert_close_mr permits a specified fraction of elements outside torch.isclose: 1% for original-versus-quantized weights and 0.1% for quantizer output versus reconstruction. The latter uses 1e-3 relative/absolute tolerances, with a source comment attributing necessary tolerance to float32 quantization versus float16 reversal of regularization. These tests do not evaluate representative calibration data or full-model quality. [source; call_65ca26b5fbc14ea39e50a5b35f6d2646, call_6b0bbddd462c44feb90157cd3ad3f343]

test_sampler.py constructs reference top-k and top-p distributions from synthetic logits and compares sampled frequencies using sum((observed-expected)^2/expected), after flooring probabilities at 1e-5. Its top-p reference retains entries whose cumulative probability is <=p and always retains the first entry. Thresholds are 0.01 for top-k and 0.02 for top-p, with sample-count caps of 10,000 and 20,000. This probability discrepancy, also used by gumbel_eval.py, is not directly a count-based Pearson chi-square test with a reported significance level. [source; call_c5a0422ba38d4db8ad44e042058123d8, call_e118ac7813bd4326a5d1089682613765]

A scalar illustrative check with reference probabilities [0.7, 0.2, 0.1] and observed frequencies [0.68, 0.22, 0.1] produced probability discrepancy 0.00257143. For 10,000 samples the corresponding count-based Pearson statistic was 25.7143, a factor of 10,000 larger. This confirms the normalization distinction without testing any sampler. The computation uses Python double precision; the inspected GPU diagnostics use float tensors, and flooring can further change the statistic. [execution; call_6993685a93164d89bf14c7050229fd61]

generator_stresstest.py repeatedly changes queue depth and checks whether generated number lists remain consecutive, printing cached-page/token counts and 'OK!' or 'Sus!'. It exercises model generation under cache reuse, but failures are printed rather than asserted and model counting errors can confound cache diagnosis. There is also a source-visible empty-queue edge: a selected target depth of zero can leave the final randint call with bounds (0, -1). Thus the script is a useful manual stress probe, not an established exhaustive paging test. [inference; call_c18497bcc93b4b4f89a821b3b7f16483]

## Uncertainty and limits

No installation, model inference, CUDA test, HumanEval evaluation, or performance benchmark was run. The successful execution checks only window-index arithmetic and an illustrative statistical formula using standard-library Python.

Example and evaluation paths refer to local model artifacts without pinned weight revisions. Several scripts hardcode cuda:1, cuda:2, or cuda:3; reproducing them requires editing paths and device selection.

The inspected dependency lists do not establish a reproducible environment: setup.py and requirements.txt differ, llama_cpp is imported but absent from requirements_eval.txt, and pytest plus its benchmark fixture are used without being listed in the inspected requirements.

Numerical tolerances and statistical cutoffs are authored acceptance criteria, not established error guarantees. Their empirical justification is not supplied by these files.

Cross-backend tokenizer equivalence, total runtime VRAM, model-quality rankings, and speedups remain unverified. Included model specifications and README performance assertions are not new measurements.
