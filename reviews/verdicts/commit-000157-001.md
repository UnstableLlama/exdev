## Reviewer-only notes (never to a teacher)

- **The added line closes nothing on the normal path.** I checked what the entry left open. Every call to
  `stc.get_tensor` in the tree is inside a module's `load`, and nothing between the first close and the new one
  calls `load`: the code in between runs forward passes, quantizes, and collects `get_tensors()`, which return
  tensors already in memory. So the handle cache is empty when the new close runs. The reload from memory further
  down can reopen a file for a key that is not in `q_tensors`, but that happens after the new close and is cleaned
  up by the existing close on the next module. Harmless, and not a defect.
- The existing close dates from `4710c012` (position 128, 2025-05-07). The entry read no ancestor entry; the 128
  entry would have told it why that line is there. Not required for a one-line change.
- Same morning as issue 38 (a 253B model with eight-way slices). The commit names "extremely large models" and
  not the issue; the entry rightly does not connect them.
