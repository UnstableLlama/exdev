## Why it is thin

This is the largest change since commit 55: ten files, a new GEMM output type, a new Hadamard kernel, a changed kernel
template and a changed return contract for every linear layer. The entry describes each mechanism accurately. It leaves
out what a reader most needs to place the commit, and each item could have been settled from the task tree or from
evidence already in the session.

1. **Whether anything uses the new precision.** The entry says the change "selects output precision before GEMM" and
   "propagates output dtype preferences", and its Impact paragraph speaks of what FP32 output avoids. It never says which
   layers of which models ask for FP32 at this commit, or whether inference changes for any existing model. The run read
   `mlp.py` at the parent and no model definition, no `attn.py`, no `linear.py` at the task.
2. **What the changed return contract does to existing callers.** Both inner forwards used to end in a conversion and
   now return the GEMM destination directly. The entry notes the cast is gone. It does not say what callers received
   before and receive now.
3. **The new intermediate dtype.** The entry closes with "End-to-end compatibility of the new GatedMLP intermediate
   dtype option with activation kernels and subsequent projections was not established." The activation kernels and
   the down projection's entry points are a few short files in the task tree, and two of the relevant checks are in diff
   sections the run had already read. This is a question the session could answer, not a limit of the evidence.
4. **Stored models with packed scales.** The entry says the constructor converts packed signs and clears `su`/`sv`. It
   does not follow that through the three methods that read those attributes, or say what path such a model took through
   the GEMM kernel before and takes now.
5. **The one closed-catalog row.** Issue 5 was offered with five matched terms and was not read. The reading rule did not
   force it (the title reports no failure), so this is not a rule breach; but issues 7 and 15 were read and reported as
   unrelated while the only row selected for this task was skipped.

## Reviewer-only notes (not for any packet or coverage request)

These are what I found on the points above. They are here so the next review has a reference, and they must not reach
the teacher.

1. No model definition, `Attention`, `MLP` or `GatedMLP` call passes an output dtype to a `Linear` at this commit. The
   `out_dtype` arguments in the model files belong to `RMSNorm` and friends. Every linear layer therefore still produces
   half, and the FP32 route is plumbing with no user yet.
2. With `interm_dtype` float32, `activation_fn_call` reaches `act_mul_kernel`, which reinterprets its pointers as half with
   no dtype check, and the down projection would then fail the half check on `A` in `hgemm` or `exl3_gemm`. The option
   cannot work as written at this commit.
3. `get_weight_tensor` tests `if self.su` on a tensor. At the parent that raises for a packed-scale model with more than
   one element. Clearing `su`/`sv` in the constructor makes that branch unreachable, so the change repairs it in passing.
4. A packed-scale model re-saved through `get_tensors` now writes `suh`/`svh` and no longer `su`/`sv`.
5. In issue 5 the maintainer says a storage change would keep existing quantized models loadable. The constructor
   conversion here is consistent with that; no link is stated upstream.
