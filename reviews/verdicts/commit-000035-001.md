## Must fix before any canonical use (not blocking ancestor retrieval)

1. **`lru_cache` on an instance method.** The draft says the list is memoized and assumes a stable model structure. It does not say what the decorator keys on. `functools.lru_cache` applied to a method caches per `self`, in a table owned by the function, so every `Model` on which `get_cache_layers` has been called stays referenced by that table (default capacity 128) after the caller drops it, along with its module list. It also hands every caller the same list object. This is standard-library behaviour reasoned from the source, not executed; whether it matters depends on how models are created and discarded, which was not assessed.
2. The draft's limit that "Attention still retrieves cache entries by `layer_idx`" deserves one more sentence: the cache list is ordered by module traversal while `layer_idx` is the block index passed at construction, so the two agree only while every cache-capable module is one attention per block in order. True for the three model classes in the tree.
